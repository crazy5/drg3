> 版本基线：`8814a3f`（main）
> 读者对象：需要对本项目进行功能改写/二次开发的工程师
> 文档性质：代码级架构参考（非使用手册）

## 1. 项目概述

**DRG 3.0 分组器**是基于国家医保局《按病组（DRG）付费 3.0 版分组方案配置信息》实现的病案分组引擎。

核心能力：

| 能力 | 说明 |
|---|---|
| 规则导入 | 国家医保局规则 xlsx → SQLite 6 张业务表（规则以文本表达式存储） |
| 单病案分组 | 三层漏斗 MDC → ADRG → DRG，实测 ~0.05ms/条 |
| 证据链输出 | 每条尝试过的规则（含未命中、短路）全程留痕，支撑医保申诉场景的可解释性 |
| 批量分组 | xlsx/csv 上传 → 后台任务 → 进度轮询 + 结果下载，单批上限 10000 条 |
| HIS 同步 | 桥接机推送病案 → 实时分组 → 回写结果与同步日志 |

### 1.1 设计哲学

1. **逻辑 / 数据 / 引擎三层分离**：6 张业务表只承载数据，规则字符串只承载逻辑，Python 代码只承载解释执行。
2. **规则即数据**：判定逻辑写成文本 DSL 表达式，非程序员也能读、能审、能改。
3. **优先级显式化**：`priority` 字段把控制流（先匹配谁）搬进数据，引擎只做"按序首命中"。
4. **证据链是一等输出**：分组结果不只是一个 DRG 编码，而是"为什么是它"的完整可复述轨迹。

## 4. 数据模型

### 4.1 规则表（与官方 xlsx 六张表严格对应）

| 表 | 主键 | 关键字段 | 说明 |
|---|---|---|---|
| `mdc_rules` | `mdc_code` | `rule_expr`, `priority`, `is_pre_mdc`, `parsed_ast` | MDC 层规则，按 priority 全局排序 |
| `adrg_rules` | `adrg_code` | `mdc_code`, `rule_expr`, `priority`, `adrg_type`, `parsed_ast` | ADRG 层，隶属某 MDC |
| `drg_rules` | `drg_code` | `adrg_code`, `rule_expr`, `priority`, `parsed_ast` | DRG 层，隶属某 ADRG；**空规则 = 继承 ADRG** |
| `set_members` | (`set_id`,`code`) | `code_name`, `code_type`(DI/OP) | 编码集合（如 `DI_B00`、`OP_AA1`），约 10 万+ 成员 |
| `cc_list` | (`diagnosis_code`,`level`) | `exclusion_table` | CC/MCC 目录及其所属排除表 |
| `exclusion_tables` | (`table_id`,`code`) | — | 排除表明细（`EX_n`） |

### 4.2 业务表

| 表 | 说明 |
|---|---|
| `cases` | 病案：8 个分组字段（zyzd/zyss/qtzd_list/qtss_list/nl/xb/xsrtl/xsrtz）+ 管理字段（入出院日期、出院科室、source） |
| `case_results` | 分组结果：`mdc_code/adrg_code/drg_code/cc_level/error_type/error_msg/evidence_json/duration_ms`，一个病案可有多条结果（重分组追加） |
| `batch_jobs` | 批量任务进度：`status(pending/running/done/failed)`, `total/processed/succeeded/fallback/failed` |
| `his_sync_logs` | HIS 每次同步一行的审计日志 |

**注意**：`init_schema()`（`db/models.py:207`）除 `create_all` 外，还对 `cases` 表做 `PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN` 补列（`admission_date`/`discharge_date`/`discharge_department`）。新增字段时要同步在这里补迁移逻辑。

## 5. DSL 规范文约

规则表达式是本项目的核心资产。手写 lexer（`parser/lexer.py`）+ 递归下降 parser（`parser/parser.py:34`）。

### 5.1 语法形态

```
# 集合成员判定
ZYZD in DI_B00                    # 主诊断属于集合
ZYSS in OP_AA1                    # 主手术属于集合
QTZD in MCC                       # 其他诊断命中 MCC 专用集
QTZD in CC                        # CC 专用集
ZYSS not in OP_ALL                # 取反
{ZYSS, QTSS} in OP2_AC1           # 多字段任一命中
ZYZD in {DI_A01, DI_B02}          # 多集合任一命中

# 数值比较
NL >= 70
XB = 1
XSRTL < 29

# 恒真
1

# 逻辑组合（and / or / not + 括号）
((NL=0) and (XSRTL>=29)) or ((NL=0) and (XSRTL<29))

# 集合计数比较（IC29 专用）
length(OP_IC2 ∩ {ZYSS, QTSS}) >= 2
```

### 5.2 Token 类型

`IDENT` / `NUMBER` / `LBRACE` / `RBRACE` / `COMMA` / `LPAREN` / `RPAREN` / `OP(= >= <= > <)` / `KW_IN` / `KW_NOT` / `KW_AND` / `KW_OR` / `KW_LENGTH` / `INTERSECT(∩)` / `EOF`

### 5.3 AST 节点（`ast_nodes.py`）

`OrNode` · `AndNode` · `NotNode` · `InCheckNode` · `CompareNode` · `LengthCompareNode` · `ConstTrueNode`

- `serialize/deserialize`：AST ↔ JSON，导入时写入 `parsed_ast` 列，启动时反序列化，**分组时零解析开销**。
- 解析失败的规则：`parsed_ast` 存 `{"error": ...}`，加载时被标记 `is_invalid=True`（详见 §7.1 历史坑）。

### 5.4 解析管线

```
rule_text → preprocess()   # 折叠反斜杠换行等
          → tokenize()     # 词法
          → Parser.parse() # 递归下降
          → Node (AST)
```

## 6. 分组引擎核心流程

### 6.1 启动期：索引构建

`app/main.py:26 lifespan` → `init_db()` → `build_index(session)` → `app.state.rule_index`

`build_index()`（`engine/index.py:70`）从 DB 一次性加载：

| 索引字段 | 结构 | 用途 |
|---|---|---|
| `sets` | `dict[str, frozenset[str]]` | 集合成员 O(1) 判定 |
| `set_index` | `dict[str, set[str]]` | code → 所属集合反查（证据展示） |
| `mcc_set` / `cc_set` | `set[str]` | CC 分级 |
| `code_to_excl` | `dict[(code, level), table_id]` | 诊断 → 排除表 |
| `exclusion` | `dict[table_id, set[str]]` | 排除表明细 |
| `mdc_rules` | `list[RuleRecord]`（priority 升序） | MDC 层遍历 |
| `adrg_rules` | `dict[mdc_code, list[RuleRecord]]` | ADRG 层按 MDC 分组 |
| `drg_rules` | `dict[adrg_code, list[RuleRecord]]` | DRG 层按 ADRG 分组 |
| `*_by_code` | `dict[code, RuleRecord]` | 编码 → 名称查询 |

> 索引是**启动期快照**，非热更新。规则数据变更后需调用 `rebuild_rule_index`（`api/deps.py:15`）或重启服务。

### 6.2 分组主流程：`group_case()`

入口：`engine/grouper/pipeline.py:66`

```
group_case(case, index):
  1. case.to_view() → CaseView（字段归一 + QTZD/QTSS 别名）
  2. EvidenceCollector 初始化（挂 case_summary）

  ① MDC 层   _match_first(index.mdc_rules, view)         首个命中
     └ 无命中 → fallback(0000)
  ② ADRG 层  _match_first(index.adrg_rules[MDC], view)    首个命中
     └ 无命中 → fallback(0000)
  ③ CC 分级  classify_cc(view, index) → MCC/CC/NONE
     └ 结果注入 case_view 的 CC_LEVEL 变量（DRG 规则可引用）
     └ _attach_cc_evidence() 把 CC 判定作为"伪规则"挂到证据树
  ④ DRG 层   _match_first(index.drg_rules[ADRG], enriched_view,
                          empty_rule_treat="match")
     └ 无命中 → fallback(0000)

  任何异常 → error_type='error', drg_code='0000'
```

### 6.3 规则遍历：`_match_first()`（`pipeline.py:137`）

按 `priority` 升序遍历，**首个命中即返回**。三个关键分支：

| 情况 | 行为 |
|---|---|
| `rule.is_invalid or rule.ast is None` | **跳过**，记证据 `kind=invalid`（防止 silent 命中，见 §7.1） |
| 空 `raw_expr` | MDC/ADRG 层：跳过（占位规则）；DRG 层（`empty_rule_treat="match"`）：**直接命中**（继承 ADRG），记 `kind=const_true` |
| `evaluate()` 抛异常 | 记 `skip_reason="evaluation error"` 后继续下一条，不中断整层 |

未命中规则也全部记入 `StageTrace.tried_rules`——这是证据链完整性的要求。

### 6.4 CC 分级：`classify_cc()`（`grouper/cc.py:55`）

最易出错的独立模块，语义：

```
main_tables = 主诊断 ZYZD 命中的所有 EX_n 排除表
对 QTZD_LIST 中每个其他诊断：
  1. 先扫 MCC：命中 mcc_set 且其排除表 ∉ main_tables → 返回 "MCC"
  2. 再扫 CC ：命中 cc_set  且其排除表 ∉ main_tables → 返回 "CC"
  3. 排除表与主诊断相同 → 跳过（这就是"排除表"的意义：同表不计并发症）
否则返回 "NONE"
```

MCC 优先于 CC。判定过程通过 `EvidenceNode` 全程留痕。

### 6.5 求值器：`evaluate()`（`runtime/evaluator.py:114`）

- **短路求值 + 证据完整性**：`OrNode` 左侧 True → 右侧标 `skipped_short_circuit`；`AndNode` 左侧 False → 同理。未求值分支在证据树中显式标记，不假装评估过。
- **`CaseView` 别名**：DSL 里写 `QTZD` 自动映射到 `QTZD_LIST`（列表任一命中）；字段名统一转大写。
- **编码口径（重要业务约束）**：所有诊断/手术码都是**医保版精确编码**，集合判定**全程不做 X 扩展剥除回退**。原因：规则集合已收录约 44% 的 X 扩展码，基础码与扩展码各自归属集合；精确码未命中即规则不适用，不能用基础码兜底强行命中。此口径在 `evaluator.py` 与 `cc.py` 中双重声明，**改写时必须保持一致**。
- `_eval_in()` 支持三种形态：单集合、多集合列表、多字段任一；特殊集合名 `MCC`/`CC` 走专用索引。
- `_eval_length()`：`length(set ∩ {vars}) op number`，唯一已知用法为 IC29。

### 6.6 证据链：`runtime/evidence.py`

三级结构：

```
EvidenceCollector
 ├─ case_summary          # 病案摘要
 ├─ stages[]: StageTrace  # MDC / ADRG / CC / DRG 各一棵
 │    └─ tried_rules[]    # 每条尝试过的规则：rule_code/raw_expr/matched/children/skip_reason
 └─ matched_path[]        # ["MDC.MDCA", "ADRG.AA1", "DRG.AA19"]
```

- `EvidenceNode`：树形节点，`child()` 建子节点、`set(**attrs)` 挂属性，与 AST 求值轨迹一一对应。
- 快照 JSON 直接写入 `case_results.evidence_json`，前端 `EvidenceTree.vue` 渲染。
- **只有命中的规则才保留完整 children**（`StageTrace.add_tried` 中 `matched=False` 不带 children），控制结果体积。

## 7. 关键设计决策与历史坑（改写必读）

### 7.1 `is_invalid` 规则绝不能 silent 命中

`index.py:166 _safe_deserialize()` 注释记载的历史 bug：

> 早期版本 parse 失败规则兜底成 `ConstTrueNode`（永真），导致该规则把所有进入该层的病案都吸进去——典型表现：某 ADRG 占比异常高到不合常理。

现行语义：`parsed_ast` 含 `"error"` 或 JSON 解析异常 → `(None, True)` → pipeline **跳过**该规则并记证据。**任何改动都不得恢复"解析失败=永真"的兜底**。

### 7.2 空规则语义分层

| 层 | 空 `rule_expr` 语义 |
|---|---|
| MDC / ADRG | 占位，跳过 |
| DRG | 该 ADRG 的默认子组，**直接命中**（继承） |

由 `_match_first(empty_rule_treat=...)` 参数控制。

### 7.3 证据链不因优化而丢弃

未命中、短路、解析失败、求值异常——四种情况都必须留痕。若改写时引入缓存/并行，注意证据收集的时序。

### 7.4 索引一致性

- 分组读 `app.state.rule_index` 快照；规则导入后必须 `rebuild_rule_index`（`api/deps.py:15`）。
- 批量任务把 `index` 作为参数持有：任务启动时的快照，运行中重建索引不影响进行中的任务。

### 7.5 ICD 编码规范化

所有入口统一 `_norm()`：`strip().upper().rstrip(".")`（`api/cases.py:22`、批量 `_rows_to_cases`、HIS 同步同理）。集合数据是大写无点号。**新增入口必须走同一规范化**。

### 7.6 CC 证据重复计算

`pipeline.py:211 _attach_cc_evidence()` 为拿证据把 `classify_cc` **重跑一遍**（`classify_cc` 在第 ③ 步已跑过一次）。注释称"开销可忽略"——改写时若 CC 判定变重，需改为一次计算双份输出。

**HIS 同步**：`POST /api/sync/from-his` → `_process_one_case()` 逐条分组 → 写 `his_sync_logs`（received/inserted/updated/succeeded/fallback/failed）。

## 9. 已知限制

1. **`length(...)` 函数规则**：曾长期不支持（README 记载 IC2 等 <0.1% 场景走兜底）；当前 `parser` 已支持 `KW_LENGTH` + `∩`，`evaluator._eval_length()` 已实现，唯一已知用法 IC29。
2. **多值分隔符**：仅支持 `,` `;`，不支持制表符（`split_multi`，`batch_grouping.py:194`）。
3. **批量任务在主进程**：`BackgroundTasks` 执行，>100 QPS 建议切独立 worker；单批上限 `MAX_BATCH=10000`。
4. **CORS 全放开**：`allow_origins=["*"]` 为开发期配置，上线前需收紧。
5. **SQLite 单文件**：无并发写优化，批量任务与在线请求共库。
